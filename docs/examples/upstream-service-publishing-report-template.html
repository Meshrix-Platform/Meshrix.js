Operation guide

Publish an upstream service from the Console

Part 1

Organization structure configuration

Establish the administrator session and publish the organization hierarchy that scopes every later permission.

  1. Step 1: Default Workbench
  2. Step 2: Organization and permission projection

Step 1: Default Workbench

Where to go
Sign in at /login and remain on the default Workbench (/).
What to do
Submit the Console administrator sign-in form and confirm that the default Workbench opens with no credential field populated.
What is produced
An authenticated Console session on the default operational Workbench.
Why this matters
Establish the human administrator identity used by every subsequent governance action.
Not executed; insert the verified Console screenshot for this exact step.

Step 2: Organization and permission projection

Where to go
Open Permissions → Organization Structure (/admin/organization-governance).
What to do
Choose the Group template, validate it, publish it, and inspect the hierarchy, template tags, and scoped administrator roles.
What is produced
A published organization baseline with five hierarchy nodes, governed tags, and matching administrator-role projections.
Why this matters
Define which organizational scope can receive credentials, discover tools, and administer subordinate resources.
Not executed; insert the verified Console screenshot for this exact step.
Part 2

Upstream service registration and publishing

Register the service descriptor and operation mapping, then publish a healthy governed revision.

  1. Step 3: Service subject
  2. Step 4: Operation impact
  3. Step 5: Published revision

Step 3: Service subject

Where to go
Open Services → Publish Service and the service information tab (/admin/publish-upstream-service).
What to do
Import the verified JSON descriptor and load it into the editor; review the service identity, protocol, target, and health route.
What is produced
A browser publishing draft bound to the exact downloadable JSON configuration.
Why this matters
Describe the upstream service through a closed, reviewable configuration before publishing it.
Not executed; insert the verified Console screenshot for this exact step.

Step 4: Operation impact

Where to go
Stay in Services → Publish Service and open Advanced JSON.
What to do
Review both conversion operations, especially the artifact_multipart request mapping and multipart maxBytes limit.
What is produced
Two governed operation definitions for immediate and approval-required conversion over the same upstream route.
Why this matters
Bind file transport, limits, risk, and approval behavior before the gateway can expose the operation.
Not executed; insert the verified Console screenshot for this exact step.

Step 5: Published revision

Where to go
Stay in Services → Publish Service (/admin/publish-upstream-service).
What to do
Select Publish and wait for the Console to report successful publication and runtime health.
What is produced
A durable service revision loaded by the gateway with healthy upstream endpoints.
Why this matters
Make the service executable only after the manifest, gateway snapshot, and permission catalog agree.
Not executed; insert the verified Console screenshot for this exact step.
Part 3

Tool permission configuration

Confirm the published tool surface and issue the least-privilege API Key that may use it.

  1. Step 6: Granted surface
  2. Step 7: Issued API Key record

Step 6: Granted surface

Where to go
Open Tools → Tool List (/admin/tool-list).
What to do
Search for the published service and confirm that its operation appears in the governed tool catalog.
What is produced
A discoverable MCP tool projection linked to the published service operation.
Why this matters
Verify that publication reached the discovery surface without bypassing organization and permission policy.
Not executed; insert the verified Console screenshot for this exact step.

Step 7: Issued API Key record

Where to go
Open Permissions → Key Distribution (/admin/api-key-distribution).
What to do
Create an organization-scoped workload key, copy it only during the one-time reveal, distribute it to the client, then dismiss the plaintext permanently.
What is produced
A redacted distributed-key record bound to the Team scope, allowed tools, capabilities, limits, and expiry.
Why this matters
Give the MCP workload a verifiable non-forgeable identity with least-privilege authority and revocation control.
Not executed; insert the verified Console screenshot for this exact step.
Part 4

MCP service request

Configure the downstream agent, complete required approval, and verify the final MCP request audit.

  1. Step 8: Downstream agent configuration
  2. Step 9: Execution decision
  3. Step 10: Execution outcome
  4. Step 11: Audit closure

Step 8: Downstream agent configuration

Where to go
Remain in Permissions → Key Distribution (/admin/api-key-distribution).
What to do
Configure the real downstream connector through MESHRIX_MCP_TOKEN or token stdin, while the client stores only the environment-variable placeholder.
What is produced
The installed connector uses the pre-issued organization-scoped API Key as its only ordinary MCP credential.
Why this matters
Bind the real downstream configuration action to a privacy-safe operator-visible handoff.
Not executed; insert the verified Console screenshot for this exact step.

Step 9: Execution decision

Where to go
Open Approval Flow and select pending operation decisions (/approval).
What to do
Inspect each convert-require-approval-debug request and approve the current decision layer.
What is produced
One bounded execution permit for each approved conversion request; no upstream conversion has run yet.
Why this matters
Separate the authorization decision from the external side effect and prevent approval from becoming standing authority.
Not executed; insert the verified Console screenshot for this exact step.

Step 10: Execution outcome

Where to go
Remain in Approval Flow and switch to all operation records.
What to do
Confirm that each approved conversion advanced to completed exactly once.
What is produced
Completed approval records correlated with one resumed conversion per request.
Why this matters
Prove that the approval was consumed once and could not replay or authorize unrelated work.
Not executed; insert the verified Console screenshot for this exact step.

Step 11: Audit closure

Where to go
Open Tools → Tool Statistics (/admin/tool-stats).
What to do
Refresh the current page and inspect the recent-call audit for both conversion branches and the client matrix.
What is produced
A closed audit trail from client request through authorization, upstream conversion, PDF artifact retrieval, and cleanup.
Why this matters
Confirm the complete MCP-to-upstream path produced the expected artifact and remained traceable without exposing protected identities.
Not executed; insert the verified Console screenshot for this exact step.
