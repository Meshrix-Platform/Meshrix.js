# 服务端交付快速落地方案

> 状态：本地临时工作报告，不属于 Better Plan 权威文件或远端发布内容。

## 结论

当前打包流程尚不能作为高信任的客户交付闭环。

现有源码包、容器镜像、镜像权威文件、校验和、证明材料、Compose 配置和操作说明分别存在；用户需要自行拼装启动步骤。仓库具备可复用的镜像、Compose、健康检查、持久化卷和优雅退出基础，但尚缺少一个客户可直接接收的完整制品、一套统一生命周期命令、一份可安全分享的诊断包，以及对最终下载制品的真实冷启动门禁。

本方案只定义快速落地计划，不代表相关能力已经实现。实施归属 Deployment checkpoint `7777571b-124a-4336-b841-425218e977d4`，在全部验收证据完成前保持 `pending`。

## 快速落地目标

客户最终只需要处理：

1. 一个服务端交付压缩包；
2. 发布级校验和与签名权威；
3. 一个统一的 `./licomesh` 命令。

目标操作路径：

```text
校验制品 -> 解压 -> ./licomesh start -> ./licomesh status
                                |-> ./licomesh doctor
                                |-> ./licomesh diagnose
                                |-> ./licomesh restart
                                `-> ./licomesh stop
```

源码包和源码目录 Compose 继续服务于开发、审计与镜像构建，但不再与客户正式交付路径竞争。

## 审计范围与结果

### 第一轮：制品完整性

| 编号 | 级别 | 问题 | 直接风险 |
| --- | --- | --- | --- |
| DEL-001 | P0 | 客户交付由镜像、源码包、校验材料、配置和文档等多个表面组成，没有一个封闭的安装单元 | 漏文件、错版本、操作口径不一致 |
| DEL-002 | P0 | 发布流程拥有不可变镜像摘要，但快速启动示例使用版本标签 | 实际启动镜像可能偏离已验收镜像 |
| DEL-003 | P1 | 缺少制品内封闭文件清单、模式和逐文件完整性校验 | 篡改、缺失、额外文件或执行权限错误无法在启动前失败 |

### 第二轮：启停与持久化

| 编号 | 级别 | 问题 | 直接风险 |
| --- | --- | --- | --- |
| DEL-004 | P0 | 没有统一生命周期入口，用户需要自行组合拉取镜像、创建卷和运行容器 | 操作易错，支持人员难以复现 |
| DEL-005 | P0 | 已配置停止宽限期，但最终客户路径没有证明优雅退出、重复启停和数据卷保留 | 停机丢状态、残留进程或重复启动冲突 |
| DEL-006 | P1 | Docker/Compose 前置条件、端口冲突、拉取缓存、健康等待和超时错误没有统一契约 | “快速拉起”没有可测量定义，故障反馈模糊 |

### 第三轮：故障诊断与隐私

| 编号 | 级别 | 问题 | 直接风险 |
| --- | --- | --- | --- |
| DEL-007 | P0 | 没有一键生成、可安全分享且有大小上限的诊断包 | 故障无法快速定位，支持往返次数增加 |
| DEL-008 | P0 | 本地日志查看与对外分享证据没有明确分界 | 日志、环境值、路径、标识符或运行数据可能被误发 |
| DEL-009 | P1 | 镜像拉取、校验、配置、端口、健康、退出、持久化和清理失败没有稳定原因码 | 用户与支持团队无法形成一致排查树 |

### 第四轮：发布门禁

| 编号 | 级别 | 问题 | 直接风险 |
| --- | --- | --- | --- |
| DEL-010 | P0 | 发布流程没有解压并冷启动客户最终下载的那个压缩包 | 仓库内验证通过，但正式制品仍可能不可用 |
| DEL-011 | P0 | 最终制品未证明重复启动、状态检查、优雅停止、重启、持久化和隔离清理 | 生命周期闭环只能靠文档推断 |
| DEL-012 | P1 | 源码包、源码 Compose 和直接镜像启动均出现在操作材料中，没有唯一客户交付权威 | 客户选择错误路径，排障口径分裂 |

## 最小落地设计

### 1. 单一服务端交付包

拟新增一个可复现的 `tar.gz` 服务端交付包，内部只包含：

```text
licomesh-server-delivery-<version>/
├── README.md
├── docker-compose.yml
├── licomesh
├── RELEASE.env
├── MANIFEST.json
└── SHA256SUMS
```

约束：

- Compose 只接受发布流程传入的 `image@sha256:<digest>`，不接受可变标签覆盖；
- 文件清单排序稳定，时间戳和模式固定，同一输入两次组装字节一致；
- `MANIFEST.json` 是封闭清单，额外文件、缺失文件、摘要不符或可执行模式错误均在 Docker 调用前失败；
- 交付包不内嵌密钥、凭据、用户配置、日志或后端运行数据；
- GitHub Release 对服务端只暴露一个客户交付压缩包，发布级校验和与签名继续作为外部信任权威。

### 2. 统一生命周期命令

拟新增的 `./licomesh` 命令只负责组合和约束 Compose，不创建第二套运行时状态权威。

| 命令 | 行为 | 必须满足的边界 |
| --- | --- | --- |
| `verify` | 校验制品清单、摘要、模式和发布镜像引用 | 不访问网络，不启动服务 |
| `start` | 前置检查、按摘要复用或拉取镜像、启动并等待健康 | 有界超时；重复执行收敛；失败返回稳定原因码 |
| `stop` | 停止接入并在宽限期内优雅退出 | 默认保留数据卷；重复执行收敛 |
| `restart` | 串行执行停止和启动 | 不并发修改 Compose 状态 |
| `status` | 输出有限状态与健康事实 | 不输出容器标识、路径或环境值 |
| `doctor` | 检查 Docker、Compose、配置、端口和镜像条件 | 只读，不修复、不启动 |
| `diagnose` | 生成可安全分享的有界诊断包 | `0600`；无日志、无运行数据、无敏感值 |
| `logs` | 本地查看有行数上限的日志 | 明确标记为不可直接分享，独立于诊断包 |

建议稳定原因码覆盖：制品校验失败、Docker 不可用、Compose 不可用、配置无效、端口占用、镜像拉取失败、启动超时、健康失败、停止超时、持久化失败和清理失败。

### 3. 隐私安全诊断包

诊断包只允许有限词表事实：

- 产品与发布版本是否有效；
- 交付包完整性是否通过；
- Docker/Compose 是否可用；
- 配置结构是否合法，不包含配置值；
- 服务是否存在、是否运行、是否健康；
- 退出、重启和 OOM 的布尔或枚举事实；
- 实际镜像是否匹配发布摘要。

诊断包禁止包含：

- 原始日志、请求、响应和业务数据；
- 容器、进程、用户、主机或设备标识；
- 本地绝对路径、私有地址和端口值；
- 环境变量值、配置内容、令牌、密钥、证书和凭据；
- 无上限列表或高基数标签。

即使服务未启动、发布配置损坏或 Docker 不可用，`diagnose` 也应输出一个合法的有限失败报告，而不是要求先修复环境。

### 4. 最终制品门禁

发布流水线必须在镜像摘要确定并完成交付包组装后，使用新建 Linux 环境验证“最终压缩包”，不得改用源码目录中的模板或脚本替代。

强制场景：

1. 校验并解压最终压缩包；
2. 仅调用包内 `./licomesh start` 完成冷启动；
3. 验证 Web Console、`status` 和 `doctor`；
4. 写入持久化标记；
5. `stop` 后再次 `start`，验证标记仍存在；
6. 执行 `restart` 并再次验证健康；
7. 生成诊断包并执行隐私扫描；
8. 停止并清理场景自有容器、网络、临时卷和文件；
9. 输出来源、制品摘要和阶段结果绑定的低基数报告；
10. 任一阶段失败、跳过或存在清理残留时阻止发布。

## 分阶段实施顺序

每个阶段是一个最小可独立验收闭环。前一阶段的聚焦验证通过后再进入下一阶段；所有改动完成后只执行一次全量回归。

### 阶段 A：交付包契约（P0）

覆盖 `DEL-001`、`DEL-002`、`DEL-003`。

主要落点：

- `packages/foundation/config/deployment/`：交付模板和机器可读入口；
- `tools/server-scripts/`：确定性组装器和静态验证器；
- `.github/workflows/release.yml`：在镜像摘要确定后组装单一服务端资产；
- 发布资产清单与脚本注册表：登记唯一制品和生成命令。

阶段验收：两次组装字节一致；镜像必须按摘要绑定；清单闭合；篡改、缺失、额外文件和错误模式均失败。

### 阶段 B：统一启停（P0）

覆盖 `DEL-004`、`DEL-005`、`DEL-006`。

主要落点：交付包内生命周期脚本、Compose 模板和命令夹具测试。

阶段验收：`verify/start/stop/restart/status/doctor` 全部存在；重复命令收敛；健康与停止等待有界；普通停止保留数据卷；失败使用稳定原因码。

### 阶段 C：诊断闭环（P0）

覆盖 `DEL-007`、`DEL-008`、`DEL-009`。

主要落点：诊断报告 schema、公共制品隐私扫描和损坏环境夹具。

阶段验收：报告大小和权限固定；恶意夹具中的密钥、路径、标识符、环境值和运行数据无法进入报告；服务损坏时仍能生成有限报告；日志命令与分享诊断严格分离。

### 阶段 D：最终制品验收（P0）

覆盖 `DEL-010`、`DEL-011`、`DEL-012`。

主要落点：发布流水线、新建 Linux 环境的最终制品验证器、Deployment index、Runbook 和 Release Template。

阶段验收：最终下载制品完成冷启动、重复启动、状态、诊断、优雅停止、重启、持久化和清理；文档只把该压缩包声明为正式客户服务端交付入口。

## 验收门槛

以下条件全部满足后，才能把该 checkpoint 从 `pending` 推进到完成：

- 正式发布只产生一个客户服务端交付压缩包；
- 压缩包与已验证的多平台镜像摘要绑定，无法被用户配置替换为标签；
- 包内文件具有封闭清单、逐文件摘要和执行模式校验；
- 一套命令覆盖校验、启动、停止、重启、状态、预检、诊断和本地日志；
- 启停可重复执行并收敛，普通停止保留持久化数据；
- 诊断包有大小、权限、字段和隐私边界，损坏环境下仍可生成；
- 发布流水线实际运行最终压缩包并验证完整生命周期；
- 篡改、错误摘要、拉取失败、健康超时、停止超时、持久化丢失、隐私泄漏和清理残留均能阻止发布；
- Deployment index、Runbook 和 Release Template 指向同一个正式交付权威；
- 聚焦测试、变更路径回归、隐私扫描和最终一次全量回归通过。

## 明确不做

- 不把源码包改造成离线依赖镜像；
- 不在生命周期脚本中复制服务端健康、存储或配置状态机；
- 不把原始日志打进可分享诊断包；
- 不默认删除客户数据卷；
- 不用可变镜像标签换取表面上的启动便利；
- 不从交付验证直接宣称整个平台、客户端或发布渠道已经就绪；
- 不保留旧客户启动路径作为长期兼容入口，迁移完成后一次性删除竞争文档和门禁。

## 回滚原则

发布前若任一阶段失败，停止该版本发布并保留上一版正式交付入口，不上传部分交付包。发布后的代码回滚仍使用上一版已签名、按摘要绑定的完整交付包；客户普通 `stop` 不删除数据卷。任何涉及数据格式变化的版本必须使用其所属存储迁移与恢复计划，本快速落地方案不自行定义数据回滚语义。

## 完成定义

用户能够从一个正式服务端压缩包开始，用一条命令启动，用同一入口完成状态检查、优雅停止、重启和脱敏诊断；发布流水线已经对这个精确压缩包完成真实冷启动与生命周期验证。只有达到这一状态，才能认为“快速拉起、统一交付、可排障”形成了可交付闭环。
