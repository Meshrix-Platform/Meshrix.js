## 1. 执行摘要

LicoMesh 已经具备较强的平台治理和供应链基础，包括：

- Operation Permission、标签策略、审批、审计和脱敏；
- 备份快照、恢复事务、回滚与完整性校验；
- 插件制品签名、不可变制品校验和显式启用；
- 固定摘要的容器基础镜像、非 root 运行用户；
- SBOM、Trivy、SLSA provenance、Sigstore 和依赖审计；
- 有界请求、日志、指标、队列和执行沙箱方面的设计约束。

这些能力说明项目并非普通的早期原型。但是，以企业私有化部署的生产标准衡量，当前平台仍缺少若干关键闭环：

1. 发布门禁、文档和运行证据尚未同时收敛；
2. 本地 Secret Store 未提供静态加密和外部密钥托管；
3. OIDC 目前只有配置读写，没有真实的企业登录链；
4. 平台状态仍以单节点 SQLite 和本地文件为主，缺少完整 HA 状态模型；
5. 生产证明默认处于不可验证的开发策略；
6. Secret 审计追加实现存在累计 O(n²) I/O；
7. 本地备份尚未形成异地、加密且具有 RPO/RTO 的灾备能力；
8. 已有面向用户的 delivery kit，但底层单节点 Compose 尚未形成完整生产安全 profile；
9. 已签名插件仍是进程内特权代码；
10. 可观测性缺少 OTLP、SIEM 和告警通知等企业集成；
11. 平台升级、回滚和完整离线交付流程缺失；
12. 连接器支持矩阵和控制台管理闭环不完整；
13. 自评能力矩阵及安全测试门禁未覆盖全部企业控制目标。

综合判断：当前平台更适合定位为“治理和供应链能力较强的单节点预发布平台内核”。但是，不能简单按照框架缺口的技术排序推进。企业用户购买的不是 Operation Permission、proof substrate、fencing 或 capability matrix 本身，而是可安装、可登录、可完成工作、可恢复、可升级和可获得支持的结果。

因此，本报告同时使用“技术风险等级”和“用户交付优先级”两条轴：高风险问题仍必须阻止超范围声明，但研发顺序首先服务于已经选定的用户场景。多副本 HA、低信任插件隔离和强证明体系应按目标客户的连续性、生态和合规要求进入优先队列，而不应在没有对应用户场景时先于基本安装、SSO、核心工作流、备份恢复和升级闭环。

## 2. 企业用户如何看待这些能力

### 2.1 企业用户购买的是结果，不是框架名称

“用户需要的能力”和“框架看起来应该具备的能力”不是互斥关系。框架能力是实现用户结果的手段，但只有在以下条件之一成立时才应该提高研发优先级：

1. 它直接解除目标用户当前无法完成的任务；
2. 它降低用户已经承担的安全、数据、停机或运维风险；
3. 它是已经承诺的部署档位、合规范围或扩展生态的必要条件；
4. 它能用用户可理解的指标证明效果，而不是只增加内部抽象或门禁数量。

反之，如果一项框架能力没有服务于明确用户旅程，也没有关闭当前风险，就应保留在架构储备或条件性能力中，不应抢占用户闭环的优先级。

### 2.4 框架术语应翻译成用户价值

| 框架术语 | 用户不会为它单独付费的原因 | 应向用户表达的价值 |
| --- | --- | --- |
| Operation Permission | 用户不关心内部权限引擎名称 | 谁可以在什么范围执行什么操作；高风险操作是否需要审批；拒绝原因是否可理解 |
| Proof substrate | 用户不关心证明对象如何组合 | 审计记录是否可信、可验证、不可静默伪造，以及发生争议时能否追溯 |
| Capability matrix | 用户不关心登记了多少能力线 | 哪些场景受支持、哪些未支持，以及每个声明是否有真实验证 |
| OTel semantic fields | 字段命名本身不能解决故障 | 能否接入现有监控平台，能否关联一次请求，告警是否真正送达值班人员 |
| Plugin signature | 签名只能证明来源和完整性 | 插件来自谁、是否经过批准、出问题时会影响多大范围，以及能否安全停用 |
| Fencing 与分布式锁 | 用户不会直接配置一致性算法 | 故障切换或重试时不会重复扣费、重复发布、覆盖新数据或产生相互矛盾的状态 |
| SBOM、provenance 与签名 | 用户不会阅读每个构建元数据字段 | 制品来源可验证、漏洞可定位、发布物未被替换且修复版本可追踪 |

### 2.5 用户交付优先级

| 级别 | 定义 | 排序规则 |
| --- | --- | --- |
| U0 | 目标用户无法采购、部署、登录、完成核心任务、保护数据、恢复或升级 | 当前产品闭环必须优先完成 |
| U1 | 初次试用可能成功，但长期运行、支持、诊断或审计不可持续 | 紧随首个用户闭环完成 |
| U2 | 只在特定规模、连续性、生态或监管条件下成为刚需 | 由明确客户档位或已承诺场景触发 |
| U3 | 提升框架完整性、工程保证或开发效率，但用户不能直接感知 | 绑定到 U0/U1 场景验收，不单独抢占产品优先级 |

技术风险等级仍用于判断是否必须阻止某项产品声明。例如，没有 HA 能力时不能发布 HA 档位；但如果首个明确支持的产品是单节点版，HA 不应先于该用户完成安装、SSO、核心工作、备份恢复和升级闭环。

### 2.6 首个应优先闭环的用户场景

建议将第一条最小可独立验收场景定义为：**企业管理员在受限网络中部署单节点平台，并让员工通过企业身份安全使用核心能力。**

完整旅程应当是：

1. 运维人员取得可验证的交付包，在受限网络或企业镜像源中完成安装；
2. 平台以 TLS、安全 Secret 和明确健康状态启动；
3. 身份管理员接入企业 IdP，完成真实登录、角色映射和会话撤销；
4. 平台管理员通过控制台配置服务、项目和权限；
5. 普通员工在受支持设备上登录并完成一个核心业务操作；
6. 运维人员能够看到指标、追踪和可行动告警；
7. 运维人员能够创建异地备份，并在空环境中完成恢复；
8. 运维人员能够升级，故障时可回滚到上一可用版本。

这条旅程直接要求优先关闭 F-01、F-02、F-03、F-07、F-08、F-10、F-11 和 F-12 的相关部分。F-04 的多副本 HA、F-09 的低信任插件隔离、F-05 的强监管 proof 和 F-13 的扩展框架门禁，应依据目标客户条件进入后续或并行验收；它们不能替代首条用户旅程本身。

### 2.7 产品排序规则

1. 先选定用户、部署环境和一条端到端任务，再决定需要哪些底层能力。
2. 每个框架工作项必须指向一个用户风险、用户步骤或可承诺产品档位。
3. 以用户指标验收：安装耗时、登录成功率、核心任务成功率、恢复时间、升级回滚成功率、告警送达率和支持诊断完整度。
4. 条件性能力必须写清触发条件。例如 HA 由关键业务连续性档位触发，插件隔离由第三方插件生态触发。
5. UI、API 和文档必须区分“已保存”“已预检”“当前可执行”和“生产已验证”，不能把框架存在误报为用户可用。
6. 不为了提高矩阵覆盖率而新增无用户闭环的功能；矩阵和门禁应跟随已选择的用户场景扩展。

## 3. 评估方法

### 3.1 证据类型

本报告将问题分为三种类型：

| 类型 | 定义 |
| --- | --- |
| 已确认实现缺陷 | 源码中存在可直接证明的错误、资源复杂度问题或不安全默认行为 |
| 企业能力缺口 | 当前实现明确未覆盖企业部署所需的能力或只提供局部基础设施 |
| 验证与声明缺口 | 门禁、文档或自评矩阵不能证明其声明范围，或者不同证据之间不一致 |

### 3.2 技术风险等级

| 风险等级 | 定义 |
| --- | --- |
| P0 | 阻止企业生产发布或可能直接影响身份、密钥、数据完整性及发布真实性 |
| P1 | 生产环境中的高风险缺陷，应在扩大部署规模或开放插件生态前关闭 |
| P2 | 产品完整性、支持范围或保证强度不足，不一定阻止受限单节点部署 |

技术风险等级用于限制产品声明和判断安全边界；用户交付优先级用于安排研发顺序。二者不应互相替代。

### 3.3 评估限制

- 本次未执行完整 `npm run verify:acceptance`。该命令是唯一可以产生 Core 最终发布就绪结论的权威入口。
- 本次未启动生产服务、外部身份提供商、外部数据库、对象存储、SIEM 或真实告警渠道。
- 所有“未发现”结论均表示当前仓库受检范围内没有相应实现或部署事实，不代表外部私有运维环境必然不存在该能力。
- 当前工作树并非干净的发布候选，因此报告不能代替对不可变提交的正式审计。

## 5. 详细发现

### F-01：发布状态、文档和运行证据尚未收敛

**风险等级：P0**

**用户交付级：U1**

**类型：验证与声明缺口**

#### 事实证据

- `SECURITY.md:5-7` 明确将仓库标记为 pre-release，直至发布门禁完成。

- 版本注册表验证可以通过，但没有捕获上述依赖与发布文档漂移。

#### 企业影响

- 部署方无法从文档、制品和验证报告得到一致的版本事实。
- 单个子验证命令成功可能被误解为平台发布就绪。
- 升级、回滚和兼容性判断可能基于错误的 Pactium 协议或数据结构版本。

#### 整改方向

1. 一次性完成 Pactium 迁移的代码、锁文件、兼容性说明、Runbook、发布模板和验证器收敛。
2. 扩展版本注册表门禁，使其验证依赖版本、协议版本、数据模式、兼容性表和发布模板的一致性。
3. 发布流水线必须消费报告的 `releaseReady` 与缺失证据集合，不能只依赖报告生成命令的退出成功。
4. 仅允许 `npm run verify:acceptance` 对不可变候选提交产生最终发布结论。

#### 验收条件

- 文档收敛报告无失败文档和缺失术语。
- 企业授权报告的缺失运行证据为零。
- 依赖、协议、模式、兼容性文档和发布模板中的 Pactium 版本完全一致。
- 新鲜的完整 acceptance 在隔离环境中成功，且报告绑定到同一不可变候选提交。

### F-02：本地 Secret Store 未提供静态加密与外部托管

**风险等级：P0**

**用户交付级：U0**

**类型：已确认实现缺陷**

#### 事实证据

- `packages/foundation/src/security/secrets/local-secret-store.mjs:514-529` 将完整 `payload` 写入本地 JSON value record。
- `packages/foundation/src/security/secrets/local-secret-storage.mjs:61-63` 仅通过私有文件权限和原子写入保护 JSON，没有加密步骤。
- `packages/foundation/src/security/artifact-signer-port.mjs:77-99` 从该存储解析签名私钥材料。
- `packages/agents/src/upstream-gateway/credential-material.mjs:204` 从同一 Secret Store 解析上游凭据。
- 备份逻辑会遍历数据根中的普通文件，Secret Store 不在排除目录中。

#### 企业影响

- 文件权限无法抵御磁盘快照、宿主机高权限读取、错误打包或备份泄漏。
- 插件制品签名私钥和上游服务凭据可能以可直接解析的形式进入本地备份。
- 缺少 KMS/Vault/HSM、密钥版本、轮换、撤销、双人控制和外部托管能力。

#### 整改方向

1. 建立唯一的 Secret Provider 端口，支持本地加密提供者和可选外部 KMS/Vault/HSM 提供者。
2. 本地提供者使用带认证的信封加密；数据密钥不得与密文同位置明文存储。
3. Secret 引用、版本、用途、租户/服务范围、轮换和撤销必须保持当前治理语义。
4. 对已有明文记录执行一次性完整迁移，迁移成功后删除旧值文件和兼容读取路径。
5. 备份只保存密文、最小元数据和恢复所需的外部密钥引用。

#### 验收条件

- 磁盘中的 Secret value record 不包含可恢复的原始凭据或私钥字段。
- 本地密钥、外部托管密钥和轮换后的旧版本均有独立集成测试。
- 备份内容检查证明 Secret 仅以密文或外部引用存在。
- 外部提供者不可用时返回稳定的阶段化错误，不回退到明文或默认密钥。
- 明文迁移后不存在旧格式读取、写入或兼容分支。

### F-03：OIDC 只有配置管理，没有真实企业登录链

**风险等级：P0**

**用户交付级：U0**

**类型：企业能力缺口**

#### 事实证据

- `packages/foundation/src/security/auth/console-auth.mjs:554-608` 的实际登录入口只接受用户名和密码。
- `packages/foundation/src/security/auth/console-auth.mjs:790-846` 仅实现 OIDC 配置读取和保存。
- 客户端密钥只保存哈希，无法用于需要客户端认证的 token exchange。
- Operation registry 只公开 `auth.oidc.get` 与 `auth.oidc.set`。
- 受检代码中未发现 authorize redirect、callback、state/nonce、token exchange、JWKS 验证或 PKCE 登录流程。
- 受检代码中未发现 SCIM、MFA/WebAuthn、SAML 或 LDAP/Active Directory 集成。

#### 企业影响

- 控制台可以显示 OIDC“已启用”，但用户无法通过企业 IdP 登录。
- 部署方可能误以为平台已经满足企业 SSO、账号停用和集中身份治理要求。
- 本地账号生命周期与企业目录生命周期无法自动收敛。

#### 整改方向

1. 在真实 OIDC 登录链完成前，将 UI 和 API 状态明确标为“仅保存配置”或移除启用声明。
2. 实现标准 Authorization Code 流程，包含 discovery、issuer/audience 校验、state、nonce、JWKS、token 时钟边界和安全 callback。
3. 明确 confidential client 与 PKCE 的支持策略，Secret 必须进入统一 Secret Provider。
4. 定义 claims、组、域和角色映射的唯一事实源及审计行为。
5. 增加 MFA/强认证接入策略，并定义本地紧急账号的受控使用与审计边界。
6. 根据企业账号治理范围补充 SCIM 或等价的账号同步/停用接口。

#### 验收条件

- 使用中立测试 IdP 完成登录、回调、登出、密钥轮换、过期 token 和无效 issuer 的端到端验证。
- 被禁用、移除或不满足域/组策略的企业账号无法建立新会话。
- UI 的“已启用”状态只在可执行登录链、Secret 和回调配置均通过预检时成立。
- OIDC 故障不会静默降级为未经批准的本地登录路径。
- 身份映射、登录、失败和管理员变更均产生脱敏审计证据。

### F-04：平台没有完整的多副本高可用状态模型

**风险等级：P0（仅当产品宣称 HA 或关键业务连续性档位）**

**用户交付级：U2；目标客户要求关键业务连续性时为 U0**

**类型：企业能力缺口**

#### 事实证据

- `docs/COMPATIBILITY.md:9` 将默认存储定义为本地 metadata 和 object storage。
- 授权、认证、组织、审计、告警、客户端注册、上传、标签和核心存储等多个状态所有者使用本地 SQLite 或文件。
- `packages/server-runtime/src/composition/queue-application-port.mjs:133-136` 只为工作队列提供可选 PostgreSQL 路径。
- `docs/functionality/SERVER-RUNTIME.md:160` 明确说明可执行服务不会从环境或持久配置构造 PostgreSQL LockManager。
- `docs/functionality/SERVER-RUNTIME.md:166` 明确说明通用 controller/storage 不提供原子 fencing 比较，也不声明 exactly-once effect。
- `docker-compose.yml` 只定义一个服务实例和一个本地持久卷。

#### 企业影响

- 无法安全运行多个等价副本承接写请求。
- 会话、限流、锁、授权状态和本地存储可能在副本间不一致。
- 租约丢失后的陈旧写入无法由通用存储层统一拒绝。
- 单节点、单卷或单宿主机故障会成为平台故障域。

#### 整改方向

1. 明确拆分“企业单节点版”和“企业 HA 版”两个可验证部署档位。
2. 单节点版必须声明容量、并发、数据规模、故障域、维护窗口和恢复目标。
3. HA 版应将所有共享可变状态外置到具有明确一致性语义的存储端口，包括认证会话、授权、审计、配置、限流、锁、队列和对象存储。
4. 为不可逆副作用引入存储层原子 fencing，陈旧 lease owner 必须无法提交。
5. 为后台任务、迁移和维护操作定义 leader/ownership、重入、幂等和故障恢复协议。
6. 生产部署需要副本、反亲和、PodDisruptionBudget 或等价故障隔离机制。

#### 验收条件

- 至少三个服务副本可同时运行并处理读写流量。
- 随机终止任意副本不会丢失已确认操作、会话或审计证据。
- 租约丢失后的陈旧 writer 在存储层被原子拒绝。
- 滚动替换期间没有重复不可逆副作用、部分授权状态或旧 schema 写入。
- HA 压力、故障注入和恢复验证覆盖数据库、对象存储、锁、队列和网络分区。

### F-05：生产证明默认使用不可验证的开发策略

**风险等级：P1**

**用户交付级：U1；强监管客户为 U0**

**类型：已确认实现缺陷**

#### 事实证据

- `packages/foundation/src/proof/proof-substrate/index.mjs:38` 将默认 evidence policy 设置为 `development`。
- `packages/foundation/src/proof/proof-substrate/index.mjs:161-168` 在没有显式配置时解析为该默认值。
- 开发签名器存在固定 fallback 字符串，见 `packages/foundation/src/proof/proof-substrate/index.mjs:80-83`。
- `docs/RUNBOOK.md:454-465` 说明默认策略产生不可验证证明。
- Dockerfile 和 Compose 没有为生产交付强制声明 production policy 或外部签名器。

#### 企业影响

- 生产部署如果遗漏配置，可能运行在不可验证的证据模式。
- 审计、审批和修复证明的信任强度依赖部署人员手工发现配置要求。
- 证明私钥没有统一接入外部密钥托管和轮换策略。

#### 整改方向

1. 保持普通用户配置为空，但为明确选择的生产部署 profile 增加启动前强制预检。

3. 缺失、过期、已撤销或不可用的签名器必须阻止监听端口开放。
4. 删除生产路径对固定开发签名器的任何可达性。
5. 将签名、轮换、验证清单和历史 key trust policy 纳入同一证据契约。

#### 验收条件

- 生产 profile 在缺少签名器时启动失败，并返回稳定、脱敏的错误码。
- 生产环境产生的所有 proof 都能被独立验证。
- 签名器轮换前后均可验证已有证据，且撤销策略行为明确。
- 容器与部署验证覆盖错误配置、缺失 Secret 和签名器不可用场景。

### F-06：Secret 审计追加存在累计 O(n²) I/O

**风险等级：P1**

**用户交付级：U1**

**类型：已确认实现缺陷**

#### 事实证据

- `packages/foundation/src/security/secrets/local-secret-storage.mjs:65-75` 在每次追加事件时读取完整 `audit.jsonl`，拼接新事件后原子重写整个文件。
- 当前实现没有该日志的最大字节数、分段、轮换、保留或压缩契约。

#### 复杂度与影响

- 第 n 次写入需要读取和重写前 n-1 条历史，累计 I/O 为 O(n²)。
- 每次追加的内存使用与历史文件大小线性增长。
- Secret 初始化、轮换和撤销延迟会随平台寿命增长。
- 大型历史可能触发磁盘压力、事件循环阻塞或资源耗尽。

#### 整改方向

1. 使用 SQLite WAL、分段 append-only log 或等价的有界持久结构。
2. 明确定义单段大小、总保留量、保留时长、归档、压缩和删除事务。
3. 保持事件顺序、并发互斥、崩溃恢复和审计不可静默丢失语义。
4. 查询侧使用索引或分段游标，禁止每次加载完整历史。
5. 将该路径纳入 priority-zero resource discipline 门禁。

#### 验收条件

- 单次追加的内存和 I/O 不随完整历史大小线性增长。
- 长时间压力测试证明存储增长受保留策略约束。
- 中断、并发写入、轮换和恢复测试不产生重复、截断或顺序错误事件。
- 资源门禁能在恢复旧的全量重写实现时稳定失败。

### F-07：本地备份尚未形成企业灾备能力

**风险等级：P1**

**用户交付级：U0**

**类型：企业能力缺口**

#### 事实证据

- `packages/foundation/src/storage/backup-contract.mjs:64-69` 将备份根固定在数据目录下的 `backups`。
- `packages/foundation/src/storage/backup-snapshot.mjs:47-67` 从同一数据根收集快照来源。
- 当前备份实现具有 SQLite online backup、文件完整性、原子发布和恢复事务，这是可靠的本地恢复基础。
- 受检部署与文档中未发现异地对象存储复制、备份加密、PITR、跨主机恢复计划、RPO/RTO 或灾难切换流程。

#### 企业影响

- 数据卷、宿主机或文件系统同时损坏时，生产数据和本地备份可能一起丢失。
- 本地 Secret 记录会按普通文件进入备份边界。
- 无法向企业客户证明最大可接受数据丢失和恢复时间。
- 当前离线恢复演练不能替代站点级灾难恢复。

#### 整改方向

1. 将本地快照与异地备份分为两个明确层级。
2. 提供加密、不可变、版本化的对象存储备份目标，支持独立凭据和最小权限。
3. 定义备份调度、保留、复制确认、完整性校验、密钥可恢复性和告警。
4. 根据数据所有者能力增加数据库 PITR 或明确声明不支持。
5. 为单节点版和 HA 版分别定义 RPO、RTO、恢复顺序和失败回退。
6. 定期执行从空主机或空集群恢复的隔离演练。

#### 验收条件

- 删除或损坏原始宿主机/卷后，可仅依赖异地备份恢复完整平台。
- 备份传输和静态存储均加密，恢复需要受控密钥授权。
- 自动演练验证数据、授权、审计、Secret 引用、对象和 proof 一致性。
- RPO/RTO 指标由真实演练测量，而不是文档估算。

### F-08：随附部署入口尚未达到生产加固闭环

**风险等级：P1**

**用户交付级：U0**

**类型：企业能力缺口**

#### 事实证据

- `apps/server/runtime/http-server.mjs:154` 创建明文 HTTP server。
- `docker-compose.yml:11-12` 要求生产环境自行放置 TLS 终止代理并实施网络隔离。
- `docs/RUNBOOK.md:35-77` 已提供面向用户的 delivery kit 启动、状态、诊断、重启和停止入口，这是部署体验的重要进展；该入口仍使用单节点 Compose 和 loopback HTTP，不能替代生产安全 profile。
- Compose 只提供单服务、单卷和 `/api/healthz` 健康检查。
- 受检仓库中未发现 Helm chart、Kustomize、Kubernetes manifests、Ingress、NetworkPolicy 或等价生产编排资产。
- Compose 未声明只读根文件系统、capability drop、`no-new-privileges`、seccomp/AppArmor、资源限制或容器 Secret。
- Dockerfile 使用固定摘要基础镜像和非 root 用户，这是已有加固优点。

#### 企业影响

- 每个部署团队必须自行设计 TLS、网络、资源和 Secret 边界，容易产生不一致配置。
- 健康检查没有完整区分进程存活、依赖就绪和业务接入就绪。
- 缺少标准资源请求/限制，无法预测密度、驱逐和过载行为。
- 无法将生产环境安装结果与仓库的可重复验证直接绑定。

#### 整改方向

1. 提供至少一种受支持的生产参考部署，同时保留自包含单节点部署。
2. 明确 TLS 终止、可信代理、Secure Cookie、外部 URL 和证书轮换契约。
3. 增加 liveness、readiness 和 startup probe，并绑定现有 admission/readiness 事实。
4. 提供资源请求/限制、只读根文件系统、临时目录、cap drop、seccomp、网络策略和 Secret 挂载。
5. 增加持久卷拓扑、备份目标、滚动停止和维护窗口说明。
6. 在全新隔离容器或集群环境中验证完整部署，而不是依赖开发机已有状态。

#### 验收条件

- 参考部署可从空环境完成安装、TLS 接入、健康检查和受控卸载。
- 安全上下文、网络策略、Secret 和资源限制具有机器可验证门禁。
- readiness 在依赖未就绪时保持关闭，liveness 不因暂时依赖故障错误重启服务。
- 部署验证覆盖证书、代理、持久化、重启、升级前检查和故障恢复。

### F-09：插件签名不能替代进程级隔离

**风险等级：P1**

**用户交付级：U2；开放第三方或低信任插件生态时为 U0**

**类型：企业能力缺口**

#### 事实证据

- `docs/functionality/SERVER-RUNTIME.md:125` 明确说明已选择的插件模块是进程内特权部署代码，不是沙箱边界。
- 签名和不可变制品验证提供来源、完整性与显式加载保证，但不能使恶意 JavaScript 安全。
- Execution Sandbox 隔离的是由可信平台或插件请求的非可信工作负载，不隔离插件模块本身。

#### 企业影响

- 被攻陷、恶意或审查失误的插件可以影响服务器进程可访问的内存、模块和主机能力。
- 插件的风险边界显著大于其 manifest 声明的业务能力。
- 企业客户无法将第三方插件视为低信任扩展。

#### 整改方向

1. 短期将所有进程内插件明确分类为“完全受信任的部署组件”，在安装与启用时展示该边界。
2. 禁止将来源签名表述为运行时隔离或恶意代码防护。
3. 长期采用独立进程、容器或等价隔离单元运行插件，通过窄 RPC/IPC 端口访问 Host 能力。
4. 对文件、网络、Secret、进程、CPU、内存、输出和生命周期应用每插件最小权限。
5. 插件崩溃、超时或资源耗尽不得影响核心控制面进程。

#### 验收条件

- 恶意测试插件无法读取未授权文件、环境、Secret、网络或其他插件状态。
- 插件终止、死循环和内存耗尽不会终止核心服务。
- Host 能力调用具有独立身份、授权、配额、超时和审计。
- 插件启用 UI、安装协议和文档准确说明实际信任等级。

### F-10：可观测性缺少企业级导出与通知闭环

**风险等级：P1**

**用户交付级：U1**

**类型：企业能力缺口**

#### 事实证据

- `tools/server-scripts/verify-enterprise-observability-coverage.mjs:33-38` 的核心 endpoint 覆盖只要求 5 个指标/追踪操作。
- 当前实现具有 OTel 对齐字段、结构化日志、局部 Prometheus 输出、trace 查询和本地 alert 状态机。
- 受检代码中未发现通用 OTLP exporter、完整 OpenTelemetry SDK/export pipeline、SIEM/syslog sink 或标准告警通知 provider。
- `packages/server-runtime/src/composition/devops/monitor-alerts.mjs` 主要维护本地告警状态，没有外部通知交付适配器。

#### 企业影响

- 企业现有 APM、日志平台和 SIEM 无法通过标准协议直接接入完整遥测。
- 告警可以进入本地 firing/acknowledged 状态，但不等于值班人员收到通知。
- 缺少统一 SLO、错误预算、容量趋势和跨组件关联视图。
- 当前“enterprise observability coverage”名称可能高估实际集成范围。

#### 整改方向

1. 提供有界、可配置的 OTLP metrics/logs/traces exporter。
2. 为安全审计提供 SIEM/syslog 或等价的稳定导出契约，并保持脱敏与租户边界。
3. 提供告警通知 provider 端口，支持重试、去重、升级、静默和交付回执。
4. 提供最小标准 dashboard、SLO、错误预算和容量指标集合。
5. 扩展可观测性门禁，区分“语义字段存在”“真实数据产生”“导出成功”和“通知送达”。

#### 验收条件

- 中立 OTLP collector 能收到日志、指标、追踪并保持 trace 关联。
- 合成故障能触发告警、完成通知交付并产生脱敏回执。
- exporter 不可用时遵守有界缓冲、丢弃、退避和磁盘保留策略。
- SIEM 导出不包含 Secret、原始私有 payload 或本机路径。
- SLO 和容量告警通过故障注入及压力验证。

### F-11：升级、回滚和完整离线交付流程缺失

**风险等级：P2**

**用户交付级：U0**

**类型：企业能力缺口**

#### 事实证据

- `docs/RUNBOOK.md:35-77` 已提供用户侧 delivery kit，但启动流程仍需按不可变摘要拉取 release image；`docs/RUNBOOK.md:108-124` 说明源码包也不包含已安装依赖和容器镜像。因此当前入口还不是包含 OCI 镜像与全部依赖的完全断网交付包。
- `npm run server:prepare:npm-cache` 只解决不稳定网络下的 npm 缓存准备，不等于完整离线交付。
- 受检仓库中未发现平台级升级预检、全局 schema 兼容矩阵、N/N-1 兼容、降级策略、蓝绿切换或版本回滚流程。
- 多个独立 SQLite store 各自维护迁移，缺少统一平台迁移事务和失败恢复说明。

#### 企业影响

- 隔离网络、受监管网络或无公共 registry 的环境无法直接完成标准安装。
- 升级失败时无法证明数据和运行状态可以安全回退。
- 多存储所有者可能在部分迁移后进入不兼容状态。
- 企业维护窗口、变更审批和应急回滚无法形成可执行流程。

#### 整改方向

1. 生成带签名清单的离线交付包，包含 OCI 镜像、SBOM、校验和、运行时依赖、插件制品和验证工具。
2. 支持企业内部 registry/mirror，并验证所有制品来源和摘要。
3. 建立平台级升级预检：版本跨度、磁盘、备份、Secret、schema、插件、容量和回滚可行性。
4. 定义每个 schema 的前向/后向兼容策略和允许的版本跨度。
5. 将备份、迁移、健康验证、切换和回滚组织为单一升级状态机。

#### 验收条件

- 在完全断网的空环境中可使用交付包安装并验证平台。
- N 到 N+1 升级、失败回滚和重新升级均有自动化演练。
- 任一迁移失败不会留下部分 store 已升级、部分 store 未升级的可服务状态。
- 升级前后配置、Secret 引用、授权、审计和 proof 保持一致。

### F-12：连接器支持矩阵和控制台管理闭环不完整

**风险等级：P2**

**用户交付级：U0；只对已选择的目标平台和核心管理员旅程生效**

**类型：企业能力缺口**

#### 事实证据

- `docs/COMPATIBILITY.md:25-35` 只将 macOS arm64 MCP Connector 标为发布目标。
- macOS x64、Linux x64/arm64 和 Windows x64/arm64 Connector 当前不在本版本支持范围。
- `docs/architecture/ARCHITECTURE.md:201` 说明控制台只暴露部分完整 Core workspace operation surface。
- `docs/architecture/ARCHITECTURE.md:204-205` 说明 Core 尚未保存一等 repository/Codespace attachment，统一项目能力组装 UI 尚未实现。

#### 企业影响

- 混合桌面和服务器环境无法获得统一的受支持客户端接入体验。
- 管理员仍需在多个分离界面或 API/CLI 表面完成平台操作。
- 产品演示或采购评估可能把底层 operation 已实现误解为完整管理工作流已完成。

#### 整改方向

1. 将连接器支持分为 published、verified、preview 和 unsupported，并为每个平台绑定真实制品和测试证据。
2. 优先覆盖企业常见的 Windows x64、Linux x64 和 macOS x64。
3. 为关键管理员旅程定义端到端闭环：身份、部署、服务发布、项目、权限、审计、备份与恢复。
4. UI 必须消费真实能力事实，未完成工作流不得显示为可用完整功能。

#### 验收条件

- 每个受支持平台都有最终制品、安装、升级、卸载、身份和连接测试。
- 支持矩阵与 release assets、CI runner 和兼容性报告自动收敛。
- 核心管理员旅程无需未记录的 API/CLI 补充步骤。
- 未实现或未验证的 UI 能力被准确标记，不产生虚假已配置或已支持状态。

### F-13：自评能力矩阵与安全测试门禁存在盲区

**风险等级：P2**

**用户交付级：U3；用于保护 U0/U1 场景的门禁应继承对应优先级**

**类型：验证与声明缺口**

#### 事实证据

- `tools/registry/open-platform-capability-matrix.json` 当前只有 11 条能力线。
- 该矩阵没有将真实 SSO、HA、DR、KMS/Vault、升级、SIEM/OTLP、离线交付列为企业发布控制目标。
- `npm run platform:audit:report` 可在上述能力未被矩阵表达时报告矩阵范围内的 `releaseReady=true`。
- `vitest.config.ts:63-82` 启用了覆盖率收集，但没有 statements、branches、functions 或 lines 阈值。
- 受检 CI workflow 中未发现独立 CodeQL/SAST、DAST 或等价静态/动态安全分析门禁。
- 现有供应链门禁已经覆盖 dependency audit、dependency review、Trivy、SBOM、provenance 和签名，这是重要优点，但不能替代应用安全分析。

#### 企业影响

- 自评结果可能只证明已登记能力，而不是企业部署所需的完整控制面。
- 新增代码可以在覆盖率显著下降时继续通过测试。
- 注入、鉴权绕过、危险数据流和动态 Web 安全问题依赖人工或现有专项测试偶然发现。

#### 整改方向

1. 建立企业控制目标注册表，至少覆盖身份、Secret、租户隔离、HA、DR、升级、运维集成、离线交付和插件信任边界。
2. 每个控制目标必须绑定实现事实、负向测试、部署证据和唯一 acceptance owner。
3. 为关键安全与治理模块设置风险分层覆盖率阈值，不使用单一全仓库数字掩盖关键路径缺口。
4. 引入独立静态安全分析和最小动态安全测试，结果进入统一发布 reducer。
5. 保持 `platform:audit:report` 的诊断定位，明确禁止其单独产生平台发布声明。

#### 验收条件

- 企业控制目标清单覆盖本报告全部发现，并具有明确 owner 与 verifier。
- 删除任一关键安全验证时，acceptance 能稳定失败。
- 关键身份、授权、Secret、协议和存储模块达到声明的分支与负向路径覆盖要求。
- 静态与动态安全分析结果经过脱敏、去重和发布 reducer 收敛。

## 6. 跨问题风险

### 6.1 数据根耦合

Secret、认证、授权、审计、对象、配置和备份大量共享同一数据根。这简化了单机部署与本地恢复，但也放大了以下共同故障：

- 单卷损坏同时影响多个安全域；
- 本地备份容易复制 Secret；
- HA 状态外置需要同时迁移多个所有者；
- 升级和恢复必须协调多个 SQLite schema 与普通文件。

### 6.2 配置真实性

OIDC“已启用”和 operation proof 开发默认说明配置展示、运行可用性与生产安全状态尚未完全由同一事实源驱动。企业控制台需要区分：

- 已保存配置；
- 已通过预检；
- 当前可执行；
- 已验证生产就绪。

### 6.3 自评范围

项目现有 verifier 数量较多，局部能力验证也较深入。但 verifier 只能证明其注册的范围。企业控制目标如果没有先进入矩阵和 acceptance DAG，就可能在大量绿色报告中保持不可见。

## 7. 用户驱动的整改顺序

### 阶段 0：先固定目标用户和最小闭环

在继续建设平台框架前，应明确首个受支持产品档位的以下事实：

- 目标企业是普通内网、受限网络还是完全隔离网络；
- 首个支持平台和连接器组合；
- 单节点是否满足首批用户，是否承诺关键业务连续性；
- 是否允许第三方或低信任插件；
- 是否面向要求可验证 proof、外部 KMS 或特定审计保留的强监管客户；
- 用户必须通过控制台完成的第一条业务与管理员旅程。

阶段出口：形成一条可以由真实企业角色从安装走到升级回滚的用户场景，并为每一步指定唯一事实源和验收指标。

### 阶段 A：让用户装得上、登得进、做得完

范围：F-01、F-02、F-03、F-08、F-11、F-12 的首个用户场景部分。

目标：

- 提供适合目标网络环境的可验证交付入口；
- 以 TLS、加密 Secret 和真实健康状态启动；
- 完成真实 OIDC 登录、角色映射、会话撤销和紧急账号策略；
- 让管理员通过控制台完成服务、项目和权限配置；
- 让目标平台上的普通用户完成一个核心业务操作；
- 提供升级预检、失败回滚和一致的版本/支持说明。

阶段出口：一名不参与源码开发的企业运维、身份管理员、平台管理员和普通员工可以共同完成首条端到端旅程，不需要未记录的代码修改或 API/CLI 补救。

### 阶段 B：让用户敢于长期运行

范围：F-06、F-07、F-10，以及首个客户范围需要的 F-05。

目标：

- 所有长期日志、审计、队列、缓存和指标具有资源与保留上限；
- 建立异地加密备份、空环境恢复演练和可测量的 RPO/RTO；
- 接入企业监控、SIEM 和告警通知，故障信息可行动；
- 为目标监管范围提供可信审计和必要的 proof 验证；
- 建立容量边界、支持诊断和常见故障恢复流程。

阶段出口：用户能够独立发现故障、获得通知、提交脱敏诊断、恢复数据并证明平台在声明容量内稳定运行。

### 阶段 C：按客户条件增加架构档位

此阶段不按“框架看起来完整”触发，而按明确客户条件触发：

| 客户条件 | 需要进入的能力 | 关联发现 |
| --- | --- | --- |
| 关键业务不能接受单节点停机 | 多副本状态外置、fencing、故障转移、滚动升级和跨故障域 DR | F-04、F-07、F-08、F-11 |
| 允许第三方或低信任插件 | 插件进程/容器隔离、每插件权限与资源边界 | F-09 |
| 强监管要求独立验证操作证据 | production proof、外部签名器、历史 key trust 与撤销 | F-05 |
| 扩展到新的终端平台 | 对应最终制品、安装/卸载、身份和协议验证 | F-12 |

阶段出口：每个新增档位都有独立支持声明、用户旅程、部署资产和验收证据，不借用其他档位的结果。

### 阶段 D：让框架门禁跟随用户场景收敛

范围：F-13 以及前述各阶段产生的验证缺口。

目标：

- capability matrix 按用户场景登记，而不是按已有模块数量登记；
- 每个 U0/U1 步骤具有成功、拒绝、依赖故障和恢复测试；
- coverage、SAST/DAST、资源门禁和 acceptance reducer 优先保护用户关键路径；
- 内部框架重构必须证明降低了用户风险、延迟、支持成本或交付时间。

阶段出口：门禁可以阻止已承诺用户场景退化，但不会因为无用户价值的框架完整度指标挤占产品闭环。

## 8. 用户场景验收清单

### 8.1 首个受支持企业单节点场景

以下条件应全部满足，才能把首个企业单节点场景视为可交付：

- [ ] 正式发布分支、版本、目标平台、网络前提和支持边界明确。
- [ ] 目标企业环境可以通过一个可验证入口完成安装、启动、状态检查、诊断和卸载。
- [ ] 文档、依赖、协议、数据模式、镜像和发布模板版本一致。
- [ ] Secret 在磁盘、备份和传输中均受加密保护，并支持轮换与受控恢复。
- [ ] OIDC 登录、回调、登出、角色映射、账号禁用和失败路径通过中立 IdP 验证。
- [ ] 平台管理员可以通过控制台完成首个服务、项目和权限配置旅程。
- [ ] 目标平台上的普通用户可以登录并完成一个核心业务操作。
- [ ] 所有配置状态准确区分已保存、已预检、当前可执行和生产已验证。
- [ ] 备份与生产数据位于不同故障域，并通过空环境恢复演练证明 RPO/RTO。
- [ ] 升级预检、升级成功、失败回滚和重新升级在隔离环境中通过。
- [ ] 长期审计、日志、队列、缓存和指标具有资源与保留上限。
- [ ] 监控、告警通知和脱敏诊断通过合成故障验证。
- [ ] 完整 Core acceptance 对同一不可变候选提交成功。

### 8.2 条件性产品档位

以下条件只在产品明确承诺相应档位时成为发布阻断：

- [ ] HA 档位：多副本、故障转移、滚动升级、陈旧 writer 拒绝和跨故障域恢复均通过验证。
- [ ] 第三方插件档位：低信任插件具有进程或容器隔离，插件故障不影响核心平台。
- [ ] 强监管档位：生产 proof 使用受托管签名器，证据可独立验证，轮换和撤销行为明确。
- [ ] 新平台档位：每个声明支持的平台都绑定最终制品及真实安装、升级、卸载和连接验证。

## 10. 结论

LicoMesh 的核心优势是治理边界、协议意识、证据收敛和供应链完整性。但企业用户不会因为框架内部拥有更多抽象、注册表或 verifier 就认为产品可用。用户首先判断的是：能否在自己的环境安装，能否使用企业账号登录，能否完成核心任务，凭据和数据是否安全，故障后能否恢复，升级失败能否回退，以及出现问题时是否有人能够快速定位。

因此，研发顺序应从首条企业用户旅程反推框架工作：先完成受限网络单节点部署、真实 SSO、核心管理员与员工流程、加密 Secret、异地恢复、监控告警和升级回滚。框架能力作为这些用户结果的实现与验收手段同步建设，而不是作为独立目标先行扩张。

多副本 HA、低信任插件隔离、强监管 proof 和更广平台支持仍然重要，但它们应由明确的客户档位触发。没有 HA 时必须诚实限制为单节点产品；没有插件隔离时必须把插件定义为完全受信任组件；没有强证明时不能承诺相应合规档位。这样既不会掩盖技术风险，也能避免为了“框架看起来完整”而推迟用户真正需要的产品闭环。

任何阶段都不应使用局部 verifier 的绿色结果替代完整 acceptance，也不应让内部框架指标脱离用户任务单独决定优先级。最终判断应同时回答两个问题：用户能否完整完成目标任务，以及支撑该任务的风险是否已经被可验证地控制。
